## 1. The benchmark set

49 questions in [`eval/retrieval.yaml`](../eval/retrieval.yaml), 11 of them the embedding stage's queries unchanged, so the numbers stay comparable with the earlier reports. Each in-scope question names the passages that answer it: a source id and the titles of its sections, resolved to character spans of the document. A chunk counts as right when it overlaps a labelled section by at least half of the smaller of the two, the chunking benchmark's rule, and for a question about one identifier it also has to contain it. A document without headings is labelled whole, with the text its right piece has to contain. Every hypothesis was written before the query was scored.

Each kind of question tests one thing:

- **paraphrase** (23): the question and its answer share a meaning but few words. Dense retrieval's home ground.
- **identifier** (14): a config key, flag or acronym. The right chunk has to contain it (`contains`), so a piece of a long section that never mentions the key does not count.
- **metadata** (6): the answer depends on something the text does not say: which project, which document, which page. Each one carries the filter its wording implies.
- **out-of-scope** (6): nothing in the corpus answers it. The right result is no passage, which only a threshold can produce: a ranking always has a top chunk.

An answer cites `[2]`; the list says what `[2]` is. `search` shows the same ranking as raw hits, scores included, and marks the ones the threshold would drop.

## 4. How similar is similar enough: the threshold

Cosine similarity is a ranking signal, not a probability, but a threshold is still the only way to return nothing. The question is whether the scores of right chunks and the best scores of unanswerable questions can be told apart. Right chunks in the top 5 score between 0.58 and 0.87 (median 0.75); the best chunk for an unanswerable question scores between 0.49 and 0.72 (median 0.66). 5 of the 6 unanswerable questions score above the lowest right chunk, so no threshold separates them perfectly.

The pick is 0.50: the most answers kept plus unanswerable questions rejected, with ties going to fewer real questions left silent and then to fewer passages shown. Rejecting those needs a signal that reads the question against the chunk, which is a reranker's job, or the answer against the passages, which is the generation stage's.

Filtering before ranking puts the right chunk in the top 5 for 4 of the 6 metadata questions, against 3 with no filter. Filtering after ranking leaves 3 with nothing: the right chunk was not in the unfiltered top 5, so there was nothing left to filter. This is the whole case for filtering first, and the reason a filter has to be part of the index's search rather than a step after it.

A filter only helps when the chunks it removes are the ones in the way. For `argocd-requirements` and `whitepaper-audience` the chunks ahead of the right one come from the same project or document, so the filter leaves the ranking as it was.

## 6. Index design: when exact search stops being enough

The index is flat: every query is scored against every chunk (384 multiplications each) and the scores are sorted. That is exact, and at this size it is nearly free next to embedding the query, which takes 6 ms. Random unit vectors of the same size show where it stops being free:

| Vectors | Memory | Score and sort |
|---:|---:|---:|
| 1,000 | 2 MB | 0.03 ms |
| 10,000 | 15 MB | 0.60 ms |
| 100,000 | 154 MB | 8.78 ms |
| 1,000,000 | 1.5 GB | 102.61 ms |

Up to 10,000 vectors the scan costs less than embedding the query; at 100,000 it costs 2 times as much and the vectors alone take 0.2 GB of memory. This corpus has 497 chunks, so the flat index stays. The time to change is when the scan, not the model, sets the latency, and the change is an approximate index (HNSW, IVF) that trades a little recall for a scan over a fraction of the vectors. Two things about this stage carry over: exact search is the recall ceiling an approximate index has to be measured against, and metadata filters are no longer a free mask. Filtering a graph before the walk breaks the walk, and filtering after it is section 5's lossy case at scale.

## 7. The pick, and what still fails

`retrieve` and `search` use `top 5 · min 0.50`, the benchmark's pick.
Three choices, each from a section above: k is 5 because the top 5 holds the answer for 38 of 43 questions and the top 10 adds 2 more for 2.0 times the tokens (section 3); the threshold is 0.50 because it keeps 38 of the 38 answers in the top 5, leaves 0 real questions silent and rejects 1 of the 6 unanswerable ones (section 4); filters apply before ranking because section 5 shows what filtering after it loses. The filter itself comes from the question: a project picker, a document the user is reading, or a page they name.

The 5 in-scope questions whose right chunk is not in the top 5:

- **"How do I ship a new version to a small share of users before everyone gets it?"** (paraphrase): the right chunk is 42nd (0.57); first instead is `k8s-deployment-md › Deployments › Updating a Deployment › Rollover (aka multiple updates in-flight)` (0.61).
- **"What is on page 9 of the Cloud Native Security Whitepaper?"** (metadata): the right chunk is 39th (0.71); first instead is `cncf-security-whitepaper › CLOUD NATIVE SECURITY WHITEPAPER, pages 1-2` (0.83). With its filter the right chunk is 1st.
- **"Who is the Cloud Native Security Whitepaper written for?"** (metadata): the right chunk is 30th (0.69); first instead is `cncf-security-whitepaper › CLOUD NATIVE SECURITY WHITEPAPER, pages 1-2` (0.84). With its filter the right chunk is 30th.
- **"What do I need before installing Argo CD?"** (metadata): the right chunk is 8th (0.74); first instead is `argocd-getting-started-stable › Getting Started › 1. Install Argo CD` (0.79). With its filter the right chunk is 8th.
- **"How do I open the Argo CD UI from my laptop without exposing the service outside the cluster?"** (paraphrase): the right chunk is 7th (0.73); first instead is `argocd-getting-started-stable › Getting Started › 3. Access Argo CD` (0.83).

What these need is a second look at the top candidates by a model that reads the question and the chunk together, which is reranking (stage 06) and for the metadata questions, a filter that removes what is actually in the way; section 5 shows that a document filter does not when the competition sits inside the same document.
