## 1. Tradeoffs: is the better option worth what it costs?

The rule: a change **buys quality** when it holds at least 2 records more (one is noise); it is **worth it** when it does so within 25% more cost per request and 25% more p95, **not worth it** past either, **free** when the quality is flat and the cost or the p95 drops by 5% or more, and **a loss** when it holds fewer. Flat quality bought with more cost or time is not worth it.

## 3. Reading the report

Quality, spend and speed are one decision, not three: the regression report says what a change held, this one says what it paid. A candidate that clears every slice gate and breaks a budget is still refused; a candidate that holds the same records cheaper or faster is the change worth shipping first. The replay row is the cache's ceiling: the same answers at no cost and retrieval's latency alone, which is what a repeated question costs in production.

```sh
uv run infra-docs-rag evaluate-efficiency                       # this report
uv run infra-docs-rag evaluate-grounding --cache --save <run>-replay   # a replay through the cache, to measure the hit share
uv run infra-docs-rag evaluate-pipeline --list-metrics           # the cost, latency and cache metrics a gate can name
```
